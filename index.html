Final-year project, 2026

AI-driven compliance agent for security retesting

My final-year project, marked First Class, compared language models as the reasoning engine of an automated security retesting agent.

Question
Which reasoning engine can be trusted to do repeatable compliance checks?
Finding
Retest sensitivity mattered most. Only one model reliably revised its judgement when a control changed between runs.
Built with
Python, sandboxed virtual machines, Cyber Essentials and ISO 27001 controls, four language models as swappable engines.
Read the full write-upClose the write-up

The problem

Checking a system against Cyber Essentials and ISO 27001 means collecting the same evidence again and again. I wanted to know whether an agent could do that repeatable work, and which reasoning engine behind it could be trusted.

What I built

The project is titled Design and Evaluation of an AI-Driven Compliance Agent for Automated Security Retesting. I designed a three-stage Python compliance agent. It interprets Cyber Essentials and ISO 27001 controls. It collects security evidence automatically inside sandboxed virtual environments. I made the reasoning engine swappable, then ran several language models through it on the same structured evidence. I did not build or train a language model. The models were the engine under comparison.

What I found

Retest sensitivity mattered most. Only one model reliably revised its judgement when a control changed between runs. Headline accuracy told me far less than how a model behaved when I tested it again.

What I would do next

I would let the agent run more than one command per control, because some controls draw their evidence from several sources. I would then finish the planned retest experiments, try larger local models to see whether the weak local results came from model size, extend the agent beyond Linux to Windows and cloud systems, and compare its judgements with those of human assessors.

Tools

Python. Sandboxed virtual environments. Several large language models, used as swappable reasoning engines. Cyber Essentials and ISO 27001 control sets.

Job search data pipeline

A tool I use every day. It collects roles from many boards, filters and ranks them, and emails me a shortlist each morning.

The problem

Roles are spread across many employer systems and job boards, and the same role often appears on several. I wanted one ranked shortlist that I could trust each morning.

What I built

The pipeline is written in Python with FastAPI and SQLite. It collects roles from the APIs of Greenhouse, Lever, Ashby, Workable, SmartRecruiters, Personio, Workday, Adzuna and The Muse. It deduplicates roles across boards. It applies hard filters for location, seniority, years of experience demanded and a salary floor. It counts how many boards carry a role and uses that as a proxy for competition. It ranks each role against a configurable profile and emails the ranked shortlist each morning. It runs unattended on a schedule, locally and daily in GitHub Actions. I extended it with a Chrome extension (Manifest V3) and an MCP server that exposes the pipeline as tools an AI assistant can call. An automated pytest suite covers it.

I built it with AI coding assistants. My part was the design, the rules for what it may and may not do, and testing each change against real employer websites.

Three decisions shaped it. It stops before any final submit, because job board terms forbid automated sending and I read everything before it goes. Personal data stays on my own machine, and identity and bank numbers are never stored. It never guesses silently. Anything unsure is marked for me to check.

What I found

Running it on real data found bugs that tests alone had missed.

  • A location filter let distant cities through, because a catch-all United Kingdom keyword outranked my list of commutable towns.
  • A salary parser read a learning budget as pay. A salary is what they pay you. Most other figures in an advert are the company's money. I taught the parser that difference.
  • An experience filter missed a requirement of between six months and three years, because it only understood digits.

What I would do next

I would widen the search to roles abroad, which needs new sources and different rules for location and pay.

Tools

Python, FastAPI, SQLite. pytest. GitHub Actions. Chrome extension (Manifest V3). MCP server. Employer and job board APIs, as listed above. AI coding assistants.

Machine learning intrusion detection pipeline

A classifier pipeline that detects DDoS traffic in network flow data.

Question
How do two common classifiers cope when the traffic changes?
Finding
Random forest looked close to perfect on validation data. On a held-out later day the two scored almost the same, and the simpler logistic regression dropped far less.
Built with
Python, pandas, scikit-learn, CIC-IDS network data.
Code
On GitHub

The problem

I wanted to detect DDoS traffic in network data and compare two common classifiers on the same task.

What I built

I wrote a Python pipeline with pandas and scikit-learn on CIC-IDS network data. It covers data preprocessing and model training. It compares a logistic regression classifier with a random forest classifier. I trained on earlier days of traffic and held out a later day as the test set, to see how each model coped with change. The code is on GitHub.

What I found

Random forest looked far better on the validation data, close to perfect. On the held-out day the two scored almost the same, and the simpler logistic regression dropped far less as the traffic changed. The lesson I took is that the model that looks best on validation data is not always the most reliable when conditions change. I reported macro F1 and ROC-AUC beside accuracy, because a model that always guessed the majority class already scored high accuracy on the imbalanced validation data.

What I would do next

I would set the alert threshold from a precision-recall analysis, test both models against simple evasion such as spoofed port and protocol fields, and evaluate them on more capture windows to measure how performance drifts over time.

Tools

Python. pandas. scikit-learn. CIC-IDS network data.

SecureCart, a secure online shop

A Django and PostgreSQL shop with login, a database-backed cart, a dummy checkout and an admin area for staff. I built it in my second year.

Controls
PBKDF2 password hashing, CSRF tokens, lockout after repeated failed logins, secure cookies, 30-minute sessions and HSTS.

On GitHub

The problem

I wanted to build an online shop where the login, cart and checkout were designed with security in mind from the start.

What I built

SecureCart is a Django web application on a PostgreSQL database. A customer can register, log in, reset a password, browse products, keep a cart that is stored in the database against their account, and go through checkout. Payment is a dummy form, so no real card is taken. Staff use an admin area to manage products and orders, and a role field on each user separates staff from customers. The code is on GitHub.

The security controls are Django's own authentication with PBKDF2 password hashing, CSRF tokens on forms, login required for the cart and checkout, and the django-axes package to lock out repeated failed logins. Session cookies are secure and HTTP-only, a session ends after 30 minutes, and HSTS is on. A small REST API for products and orders requires login by default.

What I found, looking back

I reread the code with a reviewer's eye. The products API asks for a login but not for an admin. Its viewset sets no permission class, so the default applies, which is any logged-in user. An admin-only permission class is already written in the project and imported, but it is not applied.

I tested this on a copy of the project. Logged in as a customer, I could create a product through the API. After adding one line, permission_classes = [IsAdminOrReadOnly], the same customer was refused with a 403 on create, update and delete, and the price did not change. An admin could still write, and reading still worked. One side effect: the product list can now be read without logging in. The fix is not yet in the code on GitHub.

The shop's interface is also plain, and I would redesign it.

What I would do next

I would apply the admin-only permission to the products API and keep the test I wrote, which checks that a customer cannot change a product. I would then redesign the interface, add real payments through a provider such as Stripe or PayPal, a log of what admins and customers do, and status tracking for orders, from pending to delivered.

Tools

Python, Django. PostgreSQL. Django REST framework. django-axes.

Project, second year

Secure banking database

A PostgreSQL banking database where what each user can see and change depends on their role.

Design
Four roles (bank manager, loan officer, teller, customer), each granted only the tables it needs, with row-level security, bcrypt and encrypted amounts.
Finding
Re-running the controls showed refused deletes, an audited balance update, and two customer roles getting different rows. It also showed a gap in one policy, described below.
Built with
PostgreSQL, SQL, pgcrypto, PL/pgSQL triggers.
Code
On GitHub
Read the full write-upClose the write-up

The problem

A bank's database holds data that some staff must see, fewer may change, and customers should only see their own. I wanted the database itself to enforce those rules.

What I built

I designed the schema for customers, accounts, transactions and loans, and four roles: bank manager, loan officer, teller and customer. Each role is granted only the tables it needs, and everything is revoked from the public role first. Customers can read only the account type, balance and status columns. Tellers see customers through a view that shows only the last four digits of a phone number. Row-level security policies control which rows each role sees.

Passwords are hashed with bcrypt and transaction amounts are encrypted, both with pgcrypto. Triggers write every balance change and transaction to an audit table and refuse a negative balance. Test scripts check the roles and the constraints. The code is on GitHub.

What I found

I ran the controls again on a local PostgreSQL database. A role without the right privilege was refused deletes on loans and customers, and was refused a read of the audit table. A bank manager's balance update was written to the audit table with the user, table, action and record. Two customer roles ran the same query and got different rows.

The same run showed a gap. Each customer role also saw every Active account, not only their own. The cause is in the SQL. The teller policy has no role restriction, and PostgreSQL combines permissive policies with OR, so it applies to customers too.

I tested a fix on a copy of the database. Adding TO teller to that policy stopped the leak, but it exposed two more problems. The customer policies also had no role restriction, and they turn the role name into a number, which fails for a role named teller, so the teller's own queries returned an error. And customers could not read their own transactions, because the policy checks a column they had no right to read. With TO customer added to both customer policies and one extra column grant, each customer saw only their own accounts and transactions, and the teller saw Active accounts only. Tellers see no transactions, because no policy gives them any. These changes are not yet in the code on GitHub.

What I would do next

I would apply the three changes to the project, add a test that a customer sees only their own accounts and transactions, and decide whether tellers should see any transactions. I would also keep the encryption key out of the SQL files, because it is written into the script as a placeholder, and run the role tests automatically on every change.

Tools

PostgreSQL and SQL. pgcrypto. PL/pgSQL triggers.

Four investigations: malware analysis, vulnerability analysis, detection engineering and disk image forensics.

The problem

Each one started from a staged incident, such as a trojan a user had run, a compromised web server, a vulnerable program on an exposed server or the disk image of a suspect's computer. The question each time was what happened, how far it reached, and what would catch or stop it next time. For the disk image it was whether a collection of images had been knowingly kept.

What I built

I worked through four kinds of investigation: malware analysis, vulnerability analysis with exploit development, detection engineering and disk image forensics. I used Wireshark, FLARE-VM, Procmon, Regshot, Splunk, YARA and Autopsy.

What I found

  • Malware analysis: a trojan a user had run turned out to be a ransomware loader from the TeslaCrypt family. Detonating it in FLARE-VM under Procmon and Regshot showed it dropping a second payload, changing registry values and encrypting files, which I confirmed from the NTFS change log and the ransom note it left. I wrote YARA rules that match the sample and used CAPA to confirm its obfuscation and system discovery behaviour.
  • Vulnerability analysis: a setuid program on an application server read input with an unsafe function, which left a stack buffer overflow. I confirmed it with static and dynamic analysis, then built a working exploit over the network: an information leak to get past address randomisation, a ROP chain and custom shellcode. It reached the service account but not root.
  • Detection engineering: in a staged web server compromise in Splunk's Boss of the SOC dataset, I wrote searches over HTTP traffic that found the executable the attacker uploaded and the admin password they brute-forced, by pulling the login form fields out with a regular expression and ranking them by frequency.
  • Disk image forensics: before looking at anything I checked the supplied image's MD5 and SHA1 hashes in Autopsy, so every finding rests on a verified copy. I sorted 150 images into two categories of 75, photographic and non-photographic, keeping one copy where the same file sat loose and inside a ZIP archive. Where embedded metadata existed, its dates ran from 2004 to 2022, so the images came from outside the machine, while file changes clustered between 14 and 16 February 2023 and ShellBags, the Windows record of folders opened in Explorer, showed repeated visits to the folders that held them. I found no evidence of sharing. I considered browser caching, pop-ups and malware as other explanations: I left out cache-like images and found nothing that pointed to malware, though a full malware analysis was out of scope. My opinion was that the collection was knowingly kept, stated as technical probability, with the limits listed: one static image, folder visits that do not prove a file was opened, and metadata missing from some files.

What I would do next

For the vulnerable program, I recommended a safe input function, stack canaries, position-independent code, full RELRO and removing the unneeded setuid bit. Next I would rebuild it with those fixes and rerun my exploit to confirm each one closes the path. For the disk image, my report names what it left out: deeper registry reconstruction, application execution analysis and a full malware analysis. I would add all three, starting with malware, because it is the one other explanation I could not exclude completely.

Tools

Wireshark. FLARE-VM. Procmon. Regshot. Splunk. YARA. Autopsy.
